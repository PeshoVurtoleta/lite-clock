# 0003 -- seek() is an authored edit, restart(), and the amended law #1

Status: ADOPTED (K4, v1.3.0)
Date: 2026-09-05
Findings: none (earned surface; the number was reserved at K3)

## Context

Consumers re-implement lane scrubbing the same two ways every time: to jump a
lane to a position they dispose and re-create it (churning the pool and the
generation counter), and to replay one they dispose/re-create again. Both are a
lifecycle round-trip to express what is really a single write to `positions[id]`.
K4 adds `lane.seek(p)` and `lane.restart()` so the edit is one call and the pool
never churns for a scrub.

The invariant this touches is law #1: "sim-time-driven position change happens
only via `advance()`." A naive `seek` that completed a lane, fired its callback,
or ticked the frame signal would smuggle a second mutation entry point in
through the side door and break every replay guarantee K1-K3 established.

## Decision 1 -- ADOPTED: seek is an edit, not time (law #1 amended)

`lane.seek(p)` writes the lane's position and re-bases its carry. It is an
AUTHORED EDIT, never a tick:

- Validation fails closed BEFORE the clamp: a non-finite / non-number `p` throws
  `RangeError` (`"lane.seek: position must be a finite number (got X)"`). A stale
  handle is checked FIRST, so a stale `seek` is a true no-op even for garbage
  input (matches every other handle method).
- A finite `p` clamps to `[0, duration]`.
- It writes `positions[id] = p`, `startTimes[id] = simTime - p`, and re-bases the
  cycle carry coherently: `baseStartTimes[id] = startTimes[id]`,
  `cycleCounts[id] = 0` (the K4 carry law -- everywhere 1.2.0 wrote
  `startTimes`, the base and cycle count re-base too).
- It clears `FLAG_DONE` iff the new `p < duration`. `seek(duration)` on a DONE
  lane leaves it DONE (a no-op-shaped edit).
- It NEVER starts a stopped lane. A DONE lane seeked below `duration` becomes
  PAUSED at `p`; the caller must `start()` to run it.
- It NEVER fires `onComplete`, NEVER sets `FLAG_DONE`, NEVER ticks the frame
  signal. Peeks see the new position immediately; tracked reads pull it on the
  next tick (reads track the frame signal -- unchanged law).

The amended law #1, verbatim and on the record:

> sim-time-driven position change happens only via advance(); seek() is an
> authored edit -- it never completes a lane, never fires callbacks, never ticks
> the frame signal; completion remains advance-exclusive and requires a
> compaction pass (dt=0 completes nothing).

## Decision 2 -- ADOPTED: the seek(duration) edge follows the dt=0 law

`seek(duration)` leaves `position == duration` WITHOUT completing the lane.
Completion is advance-exclusive AND requires a compaction pass. The dt=0 fast
path (`advanceBy` when `delta === 0`) SKIPS compaction -- that is the documented
"dt=0 completes nothing" law from K1. So:

- `seek(duration)` then `advance(0)` does NOT complete the lane (the dt=0 path
  skips compaction; nothing looks at the lane's `elapsed >= dur`).
- `seek(duration)` then any `advance(dt)` with a scaled `dt > 0` DOES complete
  it exactly once (`elapsed = duration + dt >= duration`, one compaction pass).
- `seek(duration)` on an ACTIVE lane completes on the next real tick.

## Option -- REJECTED: seek(duration) completes on advance(0)

The ROADMAP floated an alternative where `seek(duration)` followed by
`advance(0)` completes the lane. Rejected: it would require running the
compaction loop on the dt=0 fast path, which silently changes the documented
"dt=0 completes nothing" law -- a `advance(0)` that used to be a pure frame tick
would now fire callbacks for any lane a caller had parked at `duration`. That is
a second, hidden mutation semantic on the one entry point the whole package's
determinism rests on. The dt=0 path stays a pure tick; completion stays tied to
a real compaction pass. Callers who want the completion call `advance(anything
> 0)`.

## Interaction note -- seek during propagation does not un-queue a fire

The drain guard is generation-based (K4). An effect that calls
`lane.seek(p < duration)` on a lane that completed EARLIER IN THE SAME TICK
(during `frameSig.set` propagation) clears FLAG_DONE but does not bump the
generation, so the already-queued `onComplete` still fires in the drain. On
the record as a design choice: the completion physically occurred in the
compaction pass, and seek is an edit of position, not of history. (1.2.0's
FLAG_DONE re-check would have suppressed that fire only as an accident of its
guard mechanism; suppressing a real completion because the position was later
edited would be the lie.) Disposing the lane, as ever, cancels its remaining
fires -- dispose bumps the generation.

## Decision 3 -- ADOPTED: restart() = seek(0) + start()

`lane.restart()` is `seekLane(id, 0)` then `startLane(id)` on the current tenant;
a stale handle is a silent no-op (generation check first, like every method).

- On an ACTIVE lane: `seek(0)` re-bases to 0, and `startLane`'s early return
  (already active) keeps it active -- now running from 0. `activeCount` is
  unchanged.
- On a DONE lane: `seek(0)` clears `FLAG_DONE`, `startLane` runs it from 0.

This kills the dispose/realloc replay-churn pattern: one call replays a lane
without touching the pool, the free list, or the generation counter.

## Hot-path note

`seek`, `restart`, and the `p` validation are COLD -- they run on user edits,
never on `advance`/read hot paths. The survivor arm of the compaction loop gains
ZERO new instructions from this decision (the carry re-base reuses the D2 fields
the completion arm already maintains). The t6 alloc-dispose churn window
additionally exercises `seek`/`restart`/`stats(out)` per iteration and holds the
`maxMajor: 0` / `maxPauseMs: 4` gate -- the edit surface is zero-allocation.
